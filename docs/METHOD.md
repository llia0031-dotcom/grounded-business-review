# 方法说明

这里写清每一步怎么算、公式从哪来。拆解公式和判定规则都用公开的做法，没有自创的算法。

## 1. 数据

数据由 `bizagent/world.py` 按随机种子生成，是合成数据，不是任何平台的真实经营数据，价格、佣金率、核销率都是示意值。

| 表 | 一行是什么 |
|---|---|
| `dim_city`、`dim_category`、`dim_merchant`、`dim_store`、`dim_deal`、`dim_user`、`dim_date` | 城市、品类、商家、门店、团购商品、用户、日期 |
| `fact_traffic_daily` | 某天、某城市、某品类、某渠道的商品页访问次数 |
| `fact_order` | 一笔支付成功的团购订单 |
| `fact_redeem` | 一笔订单到店核销 |
| `fact_refund` | 一笔订单退款（主动退或过期退） |
| `fact_store_offline` | 一家门店下线的起止日期 |

生成方式是“基数 × 一串因子 + 噪声”：城市的增长趋势、星期几、节假日、每周的随机波动相乘得到访问量，访问量按转化率抽出订单，订单再按品类的核销概率和核销间隔抽出核销或退款。

三件事要知道：

- **入账时点**：支付按支付日，核销按核销日，退款按退款日。所以某一周的核销GMV 里有前几周支付的订单。
- **数据抽取从 2026-03-30 开始，周汇总从 2026-05-11 那一周开始。** 前 6 周的核销和退款有一部分属于抽取开始之前支付的订单，数字不完整，所以不进周汇总。
- **事件埋在源头。** 一个事件在一周内改一个分组的一个环节（流量、转化、供给、核销、退款），改的是生成明细之前的概率和速率，所以订单、核销、退款三张表自然对得上。同一个分组里的各个格子按同一比例变（HotSpot、Squeeze 的“涟漪效应”假设），泊松和二项抽样带来噪声。

## 2. 指标

22 个指标分四组，定义在 `metrics/metrics.yaml`，每个都有口径；`sql/metrics/` 里另有从明细表直接算的 SQL，离线自检会核对两边一致。

| 类型 | 例子 | 能不能按分组相加 |
|---|---|---|
| simple（基础量） | 访问次数、支付订单数、支付GMV、核销GMV、退款金额 | 能 |
| ratio（两个基础量相除） | 转化率、客单价、核销率、退款率、货币化率 | 不能，要拆率效应和结构效应 |
| distinct（去重计数） | 支付用户数 | 不能，只看数 |

**核销率和退款率的口径要小心**：它们是“当周核销（退款）金额 ÷ 当周支付GMV”，分子分母不是同一批订单。某个分组的支付量突然掉了，它的核销率会机械地升高，这不代表核销变好了。看同一批订单最终核销了多少，用 `sql/metrics/05_cohort_redeem.sql`。

字段名参照 dbt MetricFlow（`type`、`numerator`、`denominator`）和 Lightdash（`drivers`）。

## 3. 每周监控

规则在 `sql/monitor/weekly_alerts.sql`，一条 SQL。

1. 基线：这一周之前最近 8 个不含法定节假日的周。这一周自己不放进基线。
2. 修正 Z 分数 = 0.6745 ×（本周值 − 基线中位数）÷ MAD。MAD 是基线各周与中位数之差的绝对值的中位数。
3. 两条同时满足才算异动：修正 Z 的绝对值不低于 3.5；相对基线的变化不低于这个指标的最小幅度。
4. 九个核心指标还按城市、品类、渠道、商家类型逐个分组查，门槛更高：分组在基线期的平均占比不低于 5%，修正 Z 不低于 6，最小幅度是总量的 3 倍。

用中位数和 MAD，是因为每周只有一个点、窗口短，均值和标准差很容易被窗口里的一次异常带偏。3.5 这个阈值来自 NIST 工程统计手册引用的 Iglewicz 和 Hoaglin 的建议。指标很平稳时 MAD 接近 0，所以给 MAD 设了下限（最小幅度的十分之一）。

分组的门槛是在 30 个没有埋任何事件的周上定的（6 个随机种子、每个 5 周）：总量 0 次误报，分组 2 次误报。

已知的局限：指标有明显趋势时，中位数会落后；这份数据的增长趋势很平，所以没有做去趋势。

## 4. 拆解

代码在 `bizagent/decompose.py`，同样的算法另有纯 SQL 版（`sql/analysis/`）。对比期可以是基线（8 个基线周的平均）或上周。

**加法指标**（Adtributor 的 explanatory power，Bhagwan 等，NSDI 2014，公式 4）：

    贡献度 = 这一组的变化 ÷ 总变化

**比率指标**（Kitagawa 1955；Das Gupta 1993）。记 w 为这一组在分母里的占比，r 为这一组自己的率，R 为总的率，0 是对比期，1 是本周：

    率效应   = (w0 + w1) / 2 × (r1 − r0)
    结构效应 = (w1 − w0) × [ (r0 + r1) / 2 − (R0 + R1) / 2 ]

各组的率效应和结构效应相加，正好等于总的率的变化，没有剩余项。率效应说的是“这一组自己的率变了”，结构效应说的是“这一组的占比变了，而它的率和大盘不一样”。分开看，是为了不被占比变化骗到（辛普森悖论）。

**选哪些分组**（Adtributor 的规则）：在一个维度里，按“意外程度”从高到低取分组，单个贡献超过 10% 才取，累计超过 67% 就停；意外程度用这一组在对比期和本周的占比之间的 JS 散度算。各维度按意外程度之和排序。10% 和 67% 是论文的原值。

## 5. 三种做法

| 做法 | 怎么做 | 调模型吗 |
|---|---|---|
| 脚本 | 固定规则：从最强的异动分组开始，沿漏斗找第一个变化过门槛的环节（门店下线 → 访问 → 转化 → 退款 → 核销），用 Adtributor 再往下钻一层；一个异动如果去掉已找到的原因后不再过门槛，就不另算原因 | 否 |
| 一次提示词 | 把一组固定的查询结果（总览、异动分组、最强的三个异动指标按各维度的拆解、异动分组的体检）一次交给模型写周报 | 是，一次 |
| Agent | 模型拿到四个工具（总览、拆解、分组体检、SQL 查询），自己决定查什么、查几轮，再写周报 | 是，多轮 |

三种做法用同一套工具函数，区别只在“谁决定查什么”。

## 6. 数字核对

每次查询的结果存成一个文件（`q01.md`、`q02.md`……）。周报是一段一段的，带数字的段落必须引用数字所在的那一行。核对用 [evidence-check](https://github.com/Jason-d-e/evidence-check) 的脚本，原样放在 `vendor/`：引用的行必须一字不差地在那个文件里；这段话里的每个数字必须在引用的行里。有一段没过，整份周报不放行；模型有一次修改机会。

本项目另加三条规则，防止靠“不写数字”过关：

- “发现”段必须有具体数字；
- “原因”段必须引用至少一行；
- 周报说有异动，就必须至少有一段“发现”。

交给脚本之前做一处改写：把“百分点”换成“pp”（脚本会把“百”读成 100）。

核对能保证的是：周报里的数字都来自查询结果，没有编的、抄错的。它不能保证查询本身问对了问题，也不能保证从数字得出的结论是对的。

## 7. 出题和评分

题目由 `bizagent/scenarios.py` 生成。每道题是：一个随机种子、一个分析周、这一周埋的事件。答案（哪个分组、哪个环节）在出题时就定了。做法参照 RiskLoc 的 `generate_dataset.py` 和 InsightBench“每个场景一份答案”的组织方式。

- **监控看不见的题不要。** 一个事件如果没让监控在它直接影响的指标上报警，按监控自己的规则它就不算异动，也就没有正确答案。
- **对照题**：没有埋事件的周、含节假日的周、节后的周。

评分在 `bizagent/score.py`，只用规则：

- 说出的分组和埋的分组，如果覆盖的是同一批订单，就算对：埋的分组在基线期的订单里，至少 80% 在说出的分组里；说出的分组的订单里，至少 80% 在埋的分组里。所以“火锅连锁A”和“品类=火锅、商家=火锅连锁A”是同一个答案；一家占品类四分之一的连锁，答成“品类=火锅”只算“答粗了”。这条等价规则参照 MetricLens 的评测方案。
- **原因全对**：每个埋的事件都被找到，没有多报，也没有答粗。
- **环节也对**：在原因全对的基础上，每个原因的环节（流量、转化、供给、核销、退款、节假日）也对。
